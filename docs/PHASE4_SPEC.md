## 1. 이번 단계의 성격

Judge가 쓰는 네 물리량(응력·변위·고유진동수·좌굴)의 **포팅은 완료 단계**다.
따라서 Phase 4의 목표는 새 물리 추가가 아니라:

> **Judge 파이프라인에 실제로 꽂고(통합), 범위 밖 입력에 대해 안전하게 만들고(견고화),
> 성능 주장을 정확한 측정으로 뒷받침한다(방법론).**

## 2. 작업 항목 (우선순위 순)

### A. Judge 통합 ★ 최우선

현재 솔버는 **검증만 됐고 Judge에 연결된 적이 없다.** 이게 가장 큰 미완이다.

- **A1. `load_case` 스키마 실물 대조.**
  현재 스키마는 설계 문서 제약에서 **추정**한 것이다. Judge 저장소의 **Stage 2 코드 또는
  실제 출력 JSON 예시**를 확보해 필드명·중첩 구조·단위를 1:1 대조하고, 어긋난 부분을 수정.
  실물을 구할 수 없으면 **추정 항목 목록을 명시해 보고**하고 멈출 것. 추측으로 덮지 말 것.

- **A2. region 전달 방식 확인.**
  현재 gmsh **physical group** 전제로 구현돼 있다. Judge의 메싱 코드가 실제로 그렇게
  넘기는지 확인. 아니라면(별도 매핑 파일, 좌표 셀렉터 등) `mesh_io.py`의 region 해석만 교체.

- **A3. Stage 3a 스왑 + end-to-end 스모크.**
  Judge의 ccx 호출 지점을 `solve_structural` 로 교체하고, **케이스 1개가 Stage 3a → Stage 4
  (판정)까지 흘러가는지** 확인. measured 값이 threshold와 비교돼 판정이 나오면 성공.
  이때 **네 물리량이 모두 채워진 measured dict**가 Stage 4로 전달되는지 확인.

### B. 입력 검증 — 조용히 틀리지 않게 (안전장치)

현재 솔버의 보장 범위는 **사면체 메시 · 등방성 선형탄성 · 선형 정적/모달/좌굴**이다.
범위 밖 입력을 **에러 없이 그럴듯한 숫자로 계산하는 것**이 Judge에서 가장 위험한 실패다
(= false-pass). `solve_structural` 진입부에 검증 계층을 추가한다.

**즉시 거부(에러)** — 계산하지 말고 `solver_status`에 사유를 담아 실패 반환:
- 지원하지 않는 하중 타입 (**중력·자중·원심력·열하중** 등)
- 등방성 선형탄성이 아닌 재료 (직교이방성, 소성, 초탄성 등)
- 사면체가 아닌 요소 (hex, shell S3/S4, beam 등)
- 재료가 2종 이상이거나 **접촉(contact) 정의**가 존재
- 구속이 부족해 강체 운동이 남는 경우 (정적 해석 시)

**경고(계산은 하되 `solver_status`에 flag)**:
- ν ≥ 0.49 (거의 비압축성 → CG 수렴 악화 가능)
- 해석 후 **최대 변위가 형상 대표 치수 대비 과대** → 선형 가정 위반 의심
- 요소 품질 지표(왜곡도)가 임계 이하인 요소가 다수

원칙: **범위 밖이면 당당히 거부하는 것이 옳은 동작이다.** 수용 기준 "정직한 미수렴"과 같은 논리.

### C. 측정 방법론 보강

현재 speedup 수치에는 **하드웨어 · 알고리즘 · 구현** 세 변화가 섞여 있고, 측정 범위가
solve 구간에 한정돼 있다. 두 가지를 추가한다.

- **C1. 기여도 분해.** 같은 케이스를 `Warp(device="cpu")` 로도 실행해 3열 비교표 생성:
  `ccx(CPU)` / `Warp(CPU)` / `Warp(GPU)`.
  → Warp(CPU)/ccx = **알고리즘+구현 기여**, Warp(GPU)/Warp(CPU) = **하드웨어 기여**.

- **C2. end-to-end 측정.** solve 구간만이 아니라 **메시 로딩 → host→device 전송 → 조립 →
  solve → 결과 readback** 전체를 감싼 시간도 함께 측정해 별도 열로 보고.
  현재 수치가 "솔버 구간 기준"임을 표와 README에 명시.

### D. 응력 비교 기준 확정

검증은 **적분점 최대 von Mises** 로 했는데, ccx가 `.frd`로 내주던 값은 **노드 외삽·평균값**이다.
Judge가 실제로 소비하는 숫자가 어느 쪽이어야 하는지 확정하고, 두 방식의 차이를
응력집중 케이스(`plate_with_hole`)에서 정량화해 보고. 필요하면 노드 평균 옵션 추가.

### E. 문서 갱신

README에 좌굴 결과 반영, 보장 범위(§B) 명시, speedup의 측정 기준(§C) 각주 추가.

## 3. 수용 기준

1. **§0 현황 보고**가 표로 제출됐다.
2. **좌굴 검증** — 좌굴 하중계수가 ccx `*BUCKLE` 대비 상대오차 ≤3%, parity 표에 기록.
3. **네 물리량이 모두 담긴 measured dict**가 스키마대로 반환된다.
4. **입력 검증** — 범위 밖 입력 케이스(중력 하중, shell 요소, 2종 재료 등)를 일부러 넣었을 때
   계산하지 않고 사유와 함께 실패 반환한다. 테스트로 증명.
5. **기여도 분해표**(ccx-CPU / Warp-CPU / Warp-GPU)와 **end-to-end 시간**이 결과에 포함된다.
6. (통합 가능 시) **Stage 3a→4 스모크 1케이스 통과.** 실물 스키마를 못 구하면 이 항목은
   "차단됨(blocked)"으로 보고하고 나머지를 완료.

---

## 4. 주의점

- **A1이 막히면 A3도 막힌다.** 실제 Stage 2 출력을 못 구하면 통합은 진행 불가이므로,
  그 경우 **B·C·D를 먼저 완료**하고 A는 blocked 로 보고할 것. 추측으로 스키마를 확정하지 말 것.
- **좌굴 검증 시 주의** — 좌굴은 선행 정적해의 응력에서 기하강성을 만들므로, 정적해가
  틀리면 좌굴도 함께 틀린다. 정적 검증이 green 인 케이스로만 좌굴을 검증할 것.
- **기존 수용 기준(GPU-only CPU<20%, fp64, 정직한 미수렴)은 계속 유지**된다. 새 코드가
  이를 깨지 않는지 회귀 확인.
- 성능 측정 시 **JIT 워밍업 1회 후** 측정, `WARP_CACHE_PATH` 영구 경로 유지, ccx 스레드 수는
  **cgroup 실제 코어**로 맞출 것.
- 커밋 시 내부 설계 문서·대용량 메시 파일이 포함되지 않도록 `.gitignore` 확인.
